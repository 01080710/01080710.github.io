## Credit Card Anomaly Detection（定稿）

全頁貫穿同一個例子：客戶充值 **30、40、30 USD**（流水號 #1、#2、#3），之後退 **100 USD**。原入原出由「流水號」自然帶出，不直接丟出規則。

**完整版（約 50 秒）**

> 「客戶的所有操作都在 Client Portal。刷卡充值時，款項從 Payabl 經過 Bridger 入帳到 CRM；出金時則反過來，由營運在 Payabl 把錢退回卡上。
>
> 款項經過 Bridger 時，每一筆充值都會拿到一個唯一的流水號。小明昨天分三次充值 30、40、30 USD，就有 #1、#2、#3 三個流水號。
>
> 正因為每筆充值都有自己的流水號，原則上退款必須指定退回哪一個，這就是**原入原出**。小明今天申請退 100 USD，這張出金單（Parent）就要拆成 30→#1、40→#2、30→#3 三筆退款（Child）。
>
> 但實務上，Bridger 只把流水號傳給 Payabl，沒有傳出金單。結果 Payabl 有每筆退款的明細，卻不知道它們屬於哪張出金單；CRM 有 Parent 和 Child、卻沒有交易明細。營運在 Payabl 手動拆退款時，就可能多退一筆（30、40、30、30），或打錯金額（30、40、20）。
>
> 兩邊都沒有 API，Payabl 甚至沒有下載按鈕，所以我透過 API 逆向工程每小時自動抓兩邊報表，照原入原出逐筆比對：這張 100 USD 的單，Payabl 是不是 3 筆？每筆是不是 30、40、30？對不上的才交給營運複核。」

**20 秒版**

> 「Bridger 會替每筆刷卡充值發一個流水號，所以退款要原入原出：充值 30、40、30，退 100 時要拆成三筆、各自退回對應的流水號。但 Bridger 只把流水號傳給 Payabl、沒傳出金單，兩邊各缺一半，營運常多退或打錯金額。我用逆向 API 每小時抓兩邊報表逐筆比對，只把對不上的交給營運。」

- 「CRM API 掛了怎麼辦？」每天的報表分「產生 → 下載」兩步，各自重試 10 次；還是失敗就只跳過那一天，下一輪會重抓最近 4 天，自動補回。3/1–3/9 跳過 6 次、6 次都在下一個整點補回（05「出錯時」）。整個 CRM 停擺時，LarkSheet 上會少掉那個小時的比對時間列，看表就知道管線沒跑完。

## Deposit & Withdrawal Drop-Order Monitor（定稿）

貫穿例子是兩筆印度的實際訂單：入金 **9,301 INR**（UPI，TX-00434）、出金 **55,704 INR**（本地銀行轉帳，TX-03772）。「掉單」由「回寫」自然帶出來。

**完整版（約 50 秒）**

> 「客戶在 Client Portal 下單後，入金和出金都交給 CPS，由 CPS 對接各國渠道實際收付款；CRM 則記錄客戶看到的帳戶與訂單狀態。
>
> 錢有沒有真的動，只有 CPS 知道，所以每筆訂單的結果都要**回寫**到 CRM。先看入金：這筆 9,301 INR，CPS 先下入金指令給 CRM 建單，客戶在 UPI 付款，UPI 回呼 CPS，CPS 再回寫 CRM。問題出在回呼失敗的時候：營運會手動把 CPS 改成交易成功(人工)，但手動修改不會回寫，CRM 停在 Audit，客戶付了錢沒入帳，這就是**掉單**。
>
> 出金反過來，由 CRM 下出金指令給 CPS，CRM 這時已扣款、顯示 Completed。這筆 55,704 INR 也是回呼失敗、營運手動改成交易失敗(人工)、沒有回寫：錢沒出去，也沒退回。
>
> 麻煩的是兩邊各自看都正常：Audit 是常見的審核中，交易成功(人工)也是正常的完成狀態，只有用同一個 Order Number 對起來才看得出來。所以要做的是持續核對兩邊。動手前我先想四個問題，自己查得到的自己查，需要營運確認的主動去問：資料拿得到嗎（問營運：CPS 能直接查、CRM 用營運帳號下載報表）、對得到同一筆嗎（自己查：Order Number）、什麼算掉單（問營運，逐條對齊）、多久比一次（問營運：每小時就要知道）。規則寫好後，每小時自動比對、同一筆只派工一次。
>
> 像 11/6 上游一次上線 85 個渠道、沒測試就讓下游全部卡住那天，10 點那次揭露 450 筆、11 點再揭露 483 筆，平常單次最多 75 筆；案件直接進 LarkSheet 交給營運接手，不用等下一輪人工抽查。出金則是 10/23，英國的發卡行端批次拒絕退款，19:09 那次一口氣揭露 117 件，當天 329 件最後全部 Reverse。」

**20 秒版**

> 「CPS 實際收付款，結果要回寫給 CRM。渠道回呼失敗時，營運會手動改 CPS，但手動修改不會回寫：入金付了錢沒入帳，出金錢沒出去也沒退回。兩邊各自看都正常，要用 Order Number 對起來才看得到。我確認資料拿得到、對得起來之後，和營運把『什麼狀態算掉單』寫成規則，每小時自動比對、只派工一次。」

- 「剛成功、還在回寫中的訂單會不會被誤判？」會。判定前沒有設等待時間，這類訂單也可能被標出，由 Handler 確認後略過（04 設計重點）。

## Account Operation Automation Engine（定稿）

貫穿例子是一次真實申請（R-0055，2026-07-07）：**68 個客戶展開成 322 個帳戶**。先講動機（為什麼要查：名單上的帳戶看起來都一樣，查過才知道哪幾個不是 0，漏看就出事），再講難處（帳戶分散）。

**完整版（約 45 秒）**

> 「客戶的資料在 CRM，交易帳戶在 MetaTrader；每個帳戶的餘額、保證金與損益，要到各 regulator 自己的 CRM 後台才查得到，總共有 4 套。
>
> 帳戶關閉、強制清退、轉歸屬，這三種作業都會動到客戶的錢或歸屬，最後都匯流到同一個查詢：名單上的帳戶現在還有什麼？但名單上的帳戶看起來都一樣，大多已經是 0，只有少數還有餘額或持倉，而你光看名單分不出是哪幾個，所以每一個都得翻開來看身分、餘額與持倉。漏看一個就直接清退，客戶的持倉會被強制平倉；漏看餘額，錢沒退給客戶；漏看身分，某個後台的帳戶沒關到；轉歸屬漏看，返佣會算錯。查完之後，能不能執行由 OP 判斷。
>
> 難的是，一個客戶常常有好幾個帳戶：每個 regulator 各有一套後台，客戶在哪裡開戶，帳戶就散在哪裡。人工只能一個後台、一個帳戶地切換查詢，每個帳戶約 45 秒。
>
> 既然三種作業都卡在同一個查詢，而且都是『給名單、回傳同一組欄位』：身分、餘額、持倉三組 11 個欄位加上 3 個時間欄位，14 個通則欄位就能涵蓋大部分的申請。IT 的正式報表等不到，所以我用 API 逆向工程做成批量引擎：OP 填表，排程撿取，先驗證、再跨後台查回，成功與失敗都留紀錄。像這次申請，68 個客戶展開成 322 個帳戶，引擎一次查完。」

**20 秒版**

> 「帳戶關閉、強制清退、轉歸屬，最後都匯流到同一個查詢。名單上的帳戶看起來都一樣，查過才知道哪幾個還有餘額或持倉，漏看一個就會出事；但一個客戶的帳戶散在 4 個 regulator 的後台，人工只能逐一切換查。這些需求其實都是『給名單、回傳同一組欄位』，所以我用逆向 API 做成批量引擎，OP 填表就能一次跨後台查回。」

**被追問時**
- 成果：2026/6 上線至 11/16 成功執行 531 次，累計驗證 381,629 個帳戶，估計節省約 4,770 小時。
- 「單次上限 2,000，為什麼有批次超過？」上限是輸入的 userId 列數，一個 userId 會展開成多個帳戶。
- 「為什麼不請 IT 開權限？」有申請，但交期遙遙無期（03 方案 B）。
- 權限：用我的自動化帳號，唯讀。
- 「實際跑一次要多久？」以 2026-11-06 那批為例：5,696 個帳號、切 4 套後台，11 分半跑完（05 執行紀錄）。一般來說耗時跟名單線性成長，每套後台每 1,000 個 userId 約 25 秒（05 圖 8）。
- 「為什麼後台不能一起查？」regulator 是登入 session 上的狀態，同一個 session 一次只能停在一套後台，所以 4 套依序切換、確認後才查；並行發生在每套後台內部，所有查詢共用 20 個槽位，不會一次打出上千個請求。
- 「後台回錯誤怎麼辦？」429／5xx 遞增等待後重試，最多 10 次；401 是登入過期，直接中止不重試。
- 「20 和 10 次怎麼來的？」自己對後台測出來的：後台沒有公開限流規則，初版沒有整體上限，名單一大就回 429／5xx、登入 session 也被踢掉，所以 6/5 改成整次共用 20 個槽位；被限流後立刻重試會再被擋，所以等待時間逐次拉長。測試沒有留下各並行數的數字，被追問時只講結論，不要臨場補數字。
- 「VFSC2 是什麼？」VFSC 的第二套後台。
- 「引擎會自動擋下有餘額的帳戶嗎？」不會。引擎只把身分、餘額、持倉的欄位查回來，能不能執行由 OP 看完數字判斷。
- 「轉歸屬也一樣嗎？」是，三種作業都匯流到同一個查詢、用同一組欄位；轉歸屬漏看的後果是返佣算錯。

## Noise Camera Enforcement（定稿）

這個專案的判定由審核人員完成，我負責的是把證據送到審核人員面前的四個服務。貫穿例子是兩筆示意事件：同樣量到 **92 dBA**（標準 86 dBA），A 四項條件都符合 → 有效；B 風速 **6.3 m/s** 超過 5 m/s → 無效。

**完整版（約 45 秒）**

> 「這是一筆超標事件走過的主幹線：路邊站點量到聲音、寫進事件資料庫，接著查證天候、由審核人員判定，最後在儀表板被看見。
>
> 聲音照相是取締改裝噪音車的科技執法，但**超標不等於違規**：依規定，審核人員還要確認四項現場條件，前後三秒有沒有車、地面乾濕、風速是否小於 5 m/s、最近降雨時間，才能判定有效或無效。同樣量到 92 dBA，條件都符合就有效；當時風速超過 5 m/s，就無效。
>
> 麻煩的是，判定需要的證據散在四個地方：資料庫、檔案目錄、氣象網站和既有的工作單程式，每一件都要人工查齊。所以我把四個零散的需求放回這條流程：設備與場域管理 API 管主檔、天候查證一句話查到 CODiS 資料、事件審核 API 讓判定與出單在同一處、稽核儀表板讓結果直接看得見。」

**20 秒版**

> 「聲音照相量到超標還不算違規，依規定要確認四項現場條件才能判定，但證據散在四個地方、每件都要人工查齊。我把四個零散需求放回執法流程：主檔、天候查證、判定、儀表板各補一個斷點，讓證據一次到位。」
