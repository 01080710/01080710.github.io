## Credit Card Anomaly Detection（定稿）

全頁貫穿同一個例子：客戶充值 **30、40、30 USD**（流水號 #1、#2、#3），之後退 **100 USD**。原入原出由「流水號」自然帶出，不直接丟出規則。

**完整版（約 50 秒）**

> 「客戶的所有操作都在 Client Portal。刷卡充值時，款項從 Payabl 經過 Bridger 入帳到 CRM；出金時則反過來，由營運在 Payabl 把錢退回卡上。
>
> 款項經過 Bridger 時，每一筆充值都會拿到一個唯一的流水號。客戶分三次充值 30、40、30 USD，就有 #1、#2、#3 三個流水號。
>
> 正因為每筆充值都有自己的流水號，退款也必須指定退回哪一個，這就是**原入原出**。客戶申請退 100 USD，這張出金單（Parent）就要拆成 30→#1、40→#2、30→#3 三筆退款（Child）。
>
> 問題在於，Bridger 只把流水號傳給 Payabl，沒有傳出金單。結果 CRM 有 Parent 和 Child、卻沒有交易明細；Payabl 有每筆退款的明細，卻不知道它們屬於哪張出金單。營運在 Payabl 手動拆退款時，就可能多退一筆（30、40、30、30），或打錯金額（30、40、20）。
>
> 兩邊都沒有 API，Payabl 甚至沒有下載按鈕，所以我透過 API 逆向工程每小時自動抓兩邊報表，照原入原出逐筆比對：這張 100 USD 的單，Payabl 是不是 3 筆？每筆是不是 30、40、30？對不上的才交給營運複核。」

**20 秒版**

> 「Bridger 會替每筆刷卡充值發一個流水號，所以退款要原入原出：充值 30、40、30，退 100 時要拆成三筆、各自退回對應的流水號。但 Bridger 只把流水號傳給 Payabl、沒傳出金單，兩邊各缺一半，營運常多退或打錯金額。我用逆向 API 每小時抓兩邊報表逐筆比對，只把對不上的交給營運。」

- 「所以是 Bridger 的問題？」是串接設計的缺口：Bridger 以流水號為鍵，只把流水號傳給 Payabl、沒有傳出金單，交易明細也沒回寫 CRM。不是傳錯資料，而是兩邊各只拿到一半。我的做法是不等改介面，直接在下游把兩半對起來。

## Deposit & Withdrawal Drop-Order Monitor（定稿）

貫穿例子是兩筆印度的實際訂單：入金 **9,301 INR**（UPI，TX-00434）、出金 **55,704 INR**（本地銀行轉帳，TX-03772）。「掉單」由「回寫」自然帶出來。

**完整版（約 50 秒）**

> 「客戶在 Client Portal 下單後，入金和出金都交給 CPS，由 CPS 對接各國渠道實際收付款；CRM 則記錄客戶看到的帳戶與訂單狀態。入金由 CPS 下入金指令給 CRM，出金由 CRM 下出金指令給 CPS。
>
> 錢有沒有真的動，只有 CPS 知道，所以每筆訂單的結果都要**回寫**到 CRM。正常情況下，渠道回呼 CPS，CPS 再回寫 CRM。
>
> 問題出在渠道回呼失敗的時候：營運會手動把 CPS 改成成功或失敗，但手動修改不會回寫 CRM，這就是**掉單**。像這筆 9,301 INR 的入金，CPS 是交易成功(人工)，CRM 卻停在 Audit，客戶付了錢沒入帳；那筆 55,704 INR 的出金，CPS 是交易失敗(人工)，CRM 卻顯示 Completed，錢沒出去也沒退回。
>
> 麻煩的是兩邊各自看都正常，只有放在一起比才看得出來。所以我和營運對齊『什麼狀態組合算掉單』，寫成規則，每小時自動比對 CRM 和 CPS，同一筆只派工一次。11/6 上游異常時，兩次執行就揭露 933 筆入金掉單。」

**20 秒版**

> 「CPS 實際收付款，結果要回寫給 CRM。渠道回呼失敗時，營運會手動改 CPS，但手動修改不會回寫，客戶就付了錢沒入帳，或錢沒出去也沒退回。兩邊各自看都正常，所以我把『什麼狀態算掉單』寫成規則，每小時自動比對、只派工一次。」

| 段落 | 畫面（「照故事線看」11 步、36 拍） |
|---|---|
| 地圖 | Client Portal → CPS → 各渠道 → 入金指令（CPS→CRM）→ 出金指令（CRM→CPS） |
| 回寫 | 01 第 2 張圖 1：入金、出金兩條路的正常流程 |
| 掉單 | 圖 1：✕ 回呼失敗 → 營運手動改 → ✕ 沒有回寫（入金、出金各一次） |
| 為什麼難發現 | 01 第 3 張第一段 |
| 判定規則 | 01 第 3 張規則表逐列 |
| 對照範例 | 01 第 4 張，前兩列就是圖 1 的兩筆訂單 |
| 解決方案 | 04 架構圖：排程 → 取資料 → 比對 → 寫入與派工 |
| 操作畫面 | 05 LarkSheet 5 個工作表截圖逐張滑動：Done → Reversed → 多筆 Reverse → 心跳列中的一筆 → 整頁心跳 |
| 實際運作 | 05 執行 log 逐段亮：查 CPS → 下載 CRM 報表與對照表 → 依類型比對與寫入 |
| 輸出結果 | 05 輸出格式表：入金 → 出金 → 心跳列 |
| 成果 | 01 第 6 張圖 3：平常最多 75 → 11/6 的 450、483 |

**被追問時**
- 「剛成功、還在回寫中的訂單會不會被ㄥ誤判？」會。判定前沒有設等待時間，這類訂單也可能被標出，由 Handler 確認後略過（04 設計重點）。
- 「為什麼不請 CPS 主動通知？」時程與規格不在我們手上（03 方案 B）。
- 規模：至 2026/11/17 共揭露 15,393 筆。

## Account Operation Automation Engine（定稿）

貫穿例子是一次真實申請（R-0055，2026-07-07）：**68 個客戶展開成 322 個帳戶**。先講動機（為什麼要查），再講難處（帳戶分散）。

**完整版（約 45 秒）**

> 「客戶的資料在 CRM，交易帳戶在 MetaTrader；每個帳戶的餘額、保證金與損益，要到各 regulator 自己的 CRM 後台才查得到，總共有 4 套。
>
> 清退高風險客戶、或把客戶轉歸屬到另一個業務名下，都會動到客戶的錢，所以執行前，OP 必須先確認名單上每個帳戶的狀態。
>
> 難的是，一個客戶常常有好幾個帳戶：每個 regulator 各有一套後台，客戶在哪裡開戶，帳戶就散在哪裡。人工只能一個後台、一個帳戶地切換查詢，每個帳戶約 45 秒。
>
> 但各團隊的需求其實都是『給名單、回傳同一組欄位』。IT 的正式報表等不到，所以我用 API 逆向工程做成批量引擎：OP 填表，排程撿取，先驗證、再跨後台查回，成功與失敗都留紀錄。像這次申請，68 個客戶展開成 322 個帳戶，引擎一次查完。」

**20 秒版**

> 「清退、轉歸屬前要先查每個帳戶，但一個客戶的帳戶散在 4 個 regulator 的後台，人工只能逐一切換查。這些需求其實都是『給名單、回傳同一組欄位』，所以我用逆向 API 做成批量引擎，OP 填表就能一次跨後台查回。」

| 段落 | 畫面（「照故事線看」9 步、25 拍） |
|---|---|
| 地圖 | CRM → MetaTrader → CRM 後台 × 4 |
| 為什麼要查 | 01 第 2 張第一段 |
| 帳戶分散 | 圖 1：客戶 → 4 個後台 → 5 個帳戶 |
| 人工與引擎 | 圖 1 下方：逐一切換 vs. 一次查回 |
| 引擎流程 | 01 第 3 張圖 2 逐段亮起 |
| 對照範例 | 01 第 4 張，68 個客戶 → 322 個帳戶 |
| 實際運作 | 05 操作錄影：人工查詢 → 引擎執行（走到該拍自動靜音播放） |
| 執行紀錄 | 05 Record log：成功一列 → 兩種被攔下的申請 |
| 成果 | 05 每月使用量 |

**被追問時**
- 成果：2026/6 上線至 11/16 成功執行 531 次，累計驗證 381,629 個帳戶，估計節省約 4,770 小時。
- 「單次上限 2,000，為什麼有批次超過？」上限是輸入的 userId 列數，一個 userId 會展開成多個帳戶。
- 「為什麼不請 IT 開權限？」有申請，但交期遙遙無期（03 方案 B）。
- 權限：用我的自動化帳號，唯讀。

## Noise Camera Enforcement（定稿）

這個專案的判定由審核人員完成，我負責的是把證據送到審核人員面前的四個服務。貫穿例子是兩筆示意事件：同樣量到 **92 dBA**（標準 86 dBA），A 四項條件都符合 → 有效；B 風速 **6.3 m/s** 超過 5 m/s → 無效。

**完整版（約 45 秒）**

> 「這是一筆超標事件走過的主幹線：路邊站點量到聲音、寫進事件資料庫，接著查證天候、由審核人員判定，最後在儀表板被看見。
>
> 聲音照相是取締改裝噪音車的科技執法，但**超標不等於違規**：依規定，審核人員還要確認四項現場條件，前後三秒有沒有車、地面乾濕、風速是否小於 5 m/s、最近降雨時間，才能判定有效或無效。同樣量到 92 dBA，條件都符合就有效；當時風速超過 5 m/s，就無效。
>
> 麻煩的是，判定需要的證據散在四個地方：資料庫、檔案目錄、氣象網站和既有的工作單程式，每一件都要人工查齊。所以我把四個零散的需求放回這條流程：設備與場域管理 API 管主檔、天候查證一句話查到 CODiS 資料、事件審核 API 讓判定與出單在同一處、稽核儀表板讓結果直接看得見。」

**20 秒版**

> 「聲音照相量到超標還不算違規，依規定要確認四項現場條件才能判定，但證據散在四個地方、每件都要人工查齊。我把四個零散需求放回執法流程：主檔、天候查證、判定、儀表板各補一個斷點，讓證據一次到位。」

| 問題與定位 | 01 第 2 張最後一段 |

**被追問時**
- 「為什麼 5,605 件只有 4.2% 有效？」判定由審核人員依規定完成，無效原因的分布沒有統計，我不推測。我的模組負責讓審核人員查齊證據。
