## Credit Card Anomaly Detection（定稿）

> 「客戶只能在 Client Portal 操作。刷卡**充值**時，錢從 Payabl 經 Bridger 進到 CRM；出金時走反方向，由人員在 Payabl **退款**回卡。
>
> 信用卡出金有個規則叫『**原入原出**』：錢從哪張卡、哪筆充值進來，就要退回同一張卡、對應同一筆充值。所以客戶的一張出金單，常常要拆成好幾筆退款。
>
> 麻煩在於 Payabl 只看得到每一筆退款，CRM 只看得到整張出金單，兩邊很難對照。人員就容易出錯：一種是拆的筆數不對，例如重複退款；另一種是筆數對了，金額卻打錯。
>
> 所以我用 API 逆向工程自動抓兩邊報表，比對規則就照原入原出來設計：每張出金單，先比筆數，再逐筆比金額，只把 Payabl 已退款、CRM 卻對不上的交易交給營運複核。現在每小時自動跑一次。」

| 段落 | 畫面 |
|---|---|
| 地圖 | Quick Read 地圖：紫色虛線 Client Portal → Payabl，再沿 Recharge（往右）、Refunded（往左）兩條箭頭走一遍 |
| 原入原出 | 01 第 2 張開頭；被追問時打開名詞說明 |
| 兩種錯誤 | 圖 1：Not Same（筆數不對）、Same → 金額不同（金額錯） |
| 比對邏輯 | 01 第 3 張對照範例：P-04 重複退款 → D、P-02 金額錯 → B |

**10 秒版**：「信用卡出金要原入原出，一張出金單會拆成多筆退款，人員常配錯筆數或打錯金額。我用逆向 API 自動抓 Payabl 和 CRM 的報表，逐張出金單比筆數、比金額，只把對不上的交給營運。」

**被追問時**
- 成果：3–7 月自動執行 3,162 次；確認 29 筆錯誤退款，其中 28 筆在偵測後撤銷或要求取消（05 Result）。
- 「是 Bridger 的問題嗎？」不是。CSV 的營運備註顯示錯誤來自人工退款操作（退錯金額、重複退款、退錯訂單）；逆向工程解決的是「沒有 API、沒有下載按鈕，所以很難抓錯」。不要說成「Bridger 的 API 沒寫好」。
- 待確認：D／E 的定義是依 CSV 推論的；「原入原出」的英文譯名暫用 same-route rule。

## Deposit & Withdrawal Drop-Order Monitor（定稿）

> 「看地圖右邊這段：客戶在 Client Portal 下單，入金和出金都經過 CPS，由 CPS 對接各國渠道實際收付款，結果再回寫到 CRM，客戶看到的狀態以 CRM 為準。
>
> 如果渠道回呼失敗或上游系統異常，回寫就會中斷，形成『**掉單**』。入金是 CPS 收到錢、CRM 沒入帳，客戶付了錢卻看不到；出金是 CRM 顯示完成、CPS 實際失敗，錢沒出去也沒退回。
>
> 麻煩的是兩邊各自看都正常，只有放在一起比才看得出來；原本每天人工抽查 2 次，常常是客戶先來問。
>
> 所以我和營運對齊『什麼狀態組合算掉單』，分成 5 種案件類型寫成規則，每小時自動比對 CRM 和 CPS，同一筆只派工一次；沒有新掉單也寫一列心跳，證明監控沒中斷。」

| 段落 | 畫面 |
|---|---|
| 地圖 | 綠色虛線 Client Portal → CPS，再指 Deposit、Withdraw 兩條箭頭，最後掃過右邊 5 個渠道 |
| 掉單 | 01 背景第二點（含常見原因） |
| 規則 | 01 第 2 張掉單判定規則表 |
| 實例 | 01 第 3 張：先指 Deposit（付了錢沒入帳），再指任一筆出金（錢沒出去） |

**被追問時**
- 規模：至 2026/11/17 共揭露 15,393 筆；2026/11/6 上游故障時，兩次執行就揭露 933 筆（01 值得投入的理由）。
- 「為什麼不請 CPS 主動通知？」時程與規格不在我們手上（03 方案 B）。
- 地圖的信用卡渠道寫「Credit Card PSP」，不寫 Payabl（避免與 Credit Card 專案混淆）；但 05 輸出格式有一列渠道名稱仍含 Payabl，尚未決定是否改。

## Account Operation Automation Engine（定稿）

> 「看地圖下方這段：客戶資料在 CRM，交易帳戶在 MetaTrader，帳戶狀態要到 4 個 regulator 各自的 CRM 後台查。一個客戶常常有好幾個帳戶，分散在不同後台、不同伺服器。
>
> **清退**高風險客戶，就是關閉帳戶並結清；**轉歸屬**，是把客戶轉到另一個業務名下。這兩件事動到客戶的錢，執行前都要先確認每個帳戶的餘額、保證金、損益。原本只能逐筆切後台查，一個帳戶約 45 秒，最大一批要查 218 小時。
>
> 但這些需求看起來不同，其實都是『給一份名單，回傳同一組欄位』。IT 的正式報表等不到，所以我用 API 逆向工程做成批量引擎：OP 在 LarkSheet 填完名單，引擎先驗證輸入，再自動跨後台查回，成功與失敗都留紀錄。」

| 段落 | 畫面 |
|---|---|
| 地圖 | 從 CRM 往下指到 MetaTrader，再往右指到「CRM 後台 × 4」 |
| 概念 | 01 第 2 張「先理解兩件事」 |
| 流程 | 圖 1 引擎流程，從左到右走一遍 |
| 實例 | 01 第 3 張：68 個客戶 → 322 個帳戶 |

**被追問時**
- 成果：2026/6 上線至 11/16 成功執行 531 次，累計驗證 381,629 個帳戶，估計節省約 4,770 小時（Quick Read）。
- 「為什麼不請 IT 開權限？」有申請，但交期遙遙無期，批量案件等不了（03 方案 B）。
- 權限：用我的自動化帳號，唯讀。
- 待確認：名詞說明裡清退、轉歸屬的補充句；權限核准者；單次 2,000 筆上限的單位。

## OP Ticket Data Pipeline（草稿）

頁面尚未依故事線改寫，以下依現有頁面擬稿。

> 「看地圖左下這段：營運相關的客戶問題都在 Freshservice 開成工單。**OP 是中樞**：依主責把工單派給自己的處理群組，或轉給其他 11 個部門，最後再由 OP 收口結案。
>
> 問題是中樞看不到全貌：工單資料過去要向其他單位索取，耗時、維度常常錯置，拼不出完整的現況。
>
> 所以要解決的不是『資料不夠多』，而是 OP 自己沒有一份全量、格式固定的工單資料。我在和其他團隊共用的 API 額度內回補 Q4 的工單與對話，逐則比對後寫進每年一檔的 SQLite，再設定每日排程；重跑不會重複，中斷也能從斷點續跑。」

**頁面待補（依故事線結構）**
- 01 第 2 張：關鍵概念（OP 中樞、派單／收口、人效項目清冊）＋問題定位句，並把 04 的「比對邏輯」移到這裡。
- 01 第 3 張：對照範例，例如一張工單從開單到收口，各步驟留下的欄位與值。

## Noise Camera Enforcement（草稿）

頁面尚未依故事線改寫，以下依現有頁面擬稿。

> 「看這張主幹線圖：一筆事件從現場量到，進事件資料庫，經審核 API 判定，最後出現在稽核儀表板。
>
> **聲音照相**是取締改裝噪音車的科技執法：噪音計量到超標，攝影機同時拍下車輛。但**超標不等於違規**，審核人員要確認四項現場條件：前後三秒有沒有車、地面乾濕、風速是否小於 5 m/s、最近降雨時間，才能判定有效或無效。
>
> 這些證據原本分散在不同地方。我接到的需求看起來零散，放回執法流程，其實是同一筆事件『量到、查證、判定、看見』的四個斷點。所以我把四個服務接成一條線，讓審核人員在同一套 API 完成判定與出單，環保單位直接從儀表板看熱區與時段。」

**頁面待補（依故事線結構）**
- 01 已有「四個斷點」，02 有判定證據卡（招牌視覺）。要不要把判定證據卡往前移到 01 第 2 張，需要 Peter 決定。
- 01 第 3 張：對照範例，例如一筆有效、一筆無效事件，四項條件各自的值。
- 「為什麼有效比例只有 4.2%」很可能被問到，頁面上要有答案。
